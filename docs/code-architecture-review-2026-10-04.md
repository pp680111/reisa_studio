## 1. 总体判断

架构方向符合初始设计，模块划分已经成立，但生命周期、UI 访问边界和错误状态还没有完全闭合。对目前两个可信内置模块，结构基本够用；继续增加模块前，应优先补齐这些通用机制。

包级拆分比模块内部拆分成熟。现有目录和包结构可以继续沿用，主要工作应是让已声明的边界成为可验证的行为，而不是重建架构。

本次评审没有修改业务源码。文中的行号对应评审时的代码，后续修改可能使行号变化；定位时应同时参考符号名称。

## 5. 主要问题

优先级解释：P1 表示优先修复的行为或边界问题；P2 表示后续修复的需求缺口或工程保障问题。以下区分了临时用例已复现的问题和基于源码确认的风险路径。

### R1 · P1 · 停用没有等待在途调用结束

依据：架构 §10.2 要求拒绝新调用、撤销注册、传递取消、等待处理器结束并释放资源。

代码位置：

- [`ModuleHost.invoke` / `deactivate`](../packages/module-host/src/host.ts#L134)
- [页面调用 IPC](../apps/desktop/src/main/index.ts#L242)
- [卡片笔记停用](../modules/card-note/runtime/index.ts#L86)
- [知识库 embedding 接口](../modules/knowledge/runtime/embedding.ts#L38)

`ModuleHost.deactivate()` 撤销注册、发送取消后，直接执行模块清理，没有跟踪或等待 `invoke()` 中的处理器。临时用例确认：处理器仍在等待时，模块已经变成 `disabled`，资源清理也已完成。

页面调用绕过 `ModuleHost.invoke()`，没有取消信号或在途任务登记。卡片笔记停用仅停止定时器并关闭数据库，已启动的 Git 同步仍可能继续访问数据库。知识库工具收到的取消信号也没有继续传入检索与 embedding 请求。

另外，`invoke()` 在执行处理器前没有检查信号是否已中止。临时用例确认已取消的调用仍进入处理器，执行结束后才返回 `CANCELLED`；写操作可能已经发生。

建议：执行前检查取消；统一跟踪工具、页面和后台任务；停用时停止接收调用、协作取消、等待实际结束，再释放资源。无法中断的操作应保持 `deactivating`，不通过额外执行时间上限强行结束。

### R2 · P1 · 通用模块配置接口形成隔离旁路

依据：架构 §7.2 不提供跨模块私有配置查询接口；§8.1 要求模块自己的设置 UI 管理所属配置。

代码位置：

- [配置 IPC](../apps/desktop/src/main/index.ts#L274)
- [preload 配置桥](../apps/desktop/src/preload/index.ts#L56)
- [组合根全局注册表](../apps/desktop/src/composition/runtime.ts#L66)

配置 IPC 接受任意 `moduleId + key`，没有校验模块当前状态，也没有限定调用方所属模块。配置句柄在停用后仍保留在全局注册表中。

同一 renderer 中的组件因此具备读取、修改其他模块配置的接口，不需要所有者注册公开配置能力。这是源码确认的接口范围问题；本次没有发现现有业务页面已经主动跨模块读取配置。

两个模块的设置实际都走页面服务，通用 `moduleConfig` 没有调用方。

建议：移除未使用的通用配置入口；向模块 UI 注入绑定自身作用域的客户端；跨模块访问继续通过公开能力。作用域客户端用于工程约束，不应被描述为对恶意同进程代码的安全沙箱。

### R3 · P1 · 实时错误与历史状态不一致

依据：架构 §4.2、§10.3 与 UI 设计 §5.4 要求保持工具调用关系、真实失败和取消状态。

代码位置：

- [`collectOutcome`](../packages/agent-adapter/src/run.ts#L155)
- [`messagesToEntries`](../apps/desktop/src/renderer/conversation/ConversationView.tsx#L69)
- [发送结束后重新加载历史](../apps/desktop/src/renderer/conversation/ConversationView.tsx#L288)

适配层只在收集消息抛异常时返回 `error`，没有把 `finishReason === 'error'` 纳入失败判断。临时模型流产生错误事件后，最终仍返回 `status: 'completed'`。

历史转换把所有工具调用初始化为 `completed`，没有识别框架持久化的 `error-text` 结果。因此，工具实时显示失败，发送结束重新加载历史后会变成“已完成”。

建议：统一实时事件和历史记录的状态转换；持久化或恢复失败、取消、未完成状态；明确保留公开错误信息，避免 UI 重新解释出不同结果。

### R4 · P1 · 激活与重新配置失败缺少完整回滚

依据：架构 §6.2 要求注册失败释放资源；§10.1 要求运行基础设施失效时移除不可用注册并显示原因。

代码位置：

- [激活及失败分支](../packages/module-host/src/host.ts#L230)
- [知识库重新配置](../modules/knowledge/runtime/index.ts#L154)

模块返回 activation 后，如果能力注册校验失败，宿主不会调用该 activation 的 `deactivate()`。临时用例确认清理函数没有执行，模块却进入 `failed`。

知识库重新配置先关闭旧服务，再初始化新服务。故障注入确认：新初始化失败后，模块内部服务不可用，但宿主仍为 `active`、继续公开四个工具。

建议：明确激活期间资源回滚责任；注册校验失败清理已取得的 activation；重新配置串行化，并提供恢复旧服务或报告基础设施故障的路径；失败后撤销不可用能力、同步宿主状态。

### R5 · P2 · 启用状态默认值不一致，运行状态有多份来源

依据：架构 §8.1 要求宿主管理启用状态；UI 设计 §7 要求开关、导航、能力及生命周期状态一致。

代码位置：

- [启动默认启用集合](../apps/desktop/src/composition/runtime.ts#L129)
- [启停 IPC](../apps/desktop/src/main/index.ts#L173)
- [renderer 初始能力及状态加载](../apps/desktop/src/renderer/shell/AppShell.tsx#L98)
- [renderer 启停处理](../apps/desktop/src/renderer/shell/AppShell.tsx#L193)

启动时配置缺失表示默认启用全部模块，启停 IPC 却把缺失配置视为 `[]`。首次运行停用知识库时，会把启用清单保存为 `[]`；卡片笔记当时仍运行，但重启后也会被停用。这一结果由源码中的两处默认值直接确定，本次没有额外执行重启场景。

renderer 还有 localStorage 启用列表、运行状态和能力缓存。启停后没有刷新 `liveCapabilities`，也没有订阅宿主中间状态；初始模块状态映射未保留失败原因。模块管理无法完整反映正在激活、正在停用和失败原因。

建议：以宿主为唯一运行状态来源；统一缺失配置的语义，持久化完整启用集合；同步生命周期状态、错误原因和能力集合，处理期间避免重复操作。

### R6 · P2 · 停用模块的页面只隐藏，没有卸载

依据：架构 §10.1、§10.2 要求停用时卸载 UI 贡献。

代码位置：

- [模块页面挂载](../apps/desktop/src/renderer/shell/AppShell.tsx#L390)
- [知识库轮询](../modules/knowledge/ui/KnowledgePage.tsx#L96)
- [卡片笔记轮询](../modules/card-note/ui/BooksView.tsx#L53)

宿主始终挂载全部模块页面，使用 `hidden` 控制显示。两个模块的五秒轮询因此在停用后仍继续执行，页面保留旧数据和错误状态；启动时未启用的模块页面也会挂载。

建议：可以保留已启用页面的编辑状态，但停用时应卸载或显式停止副作用；重新启用时重新获取运行状态。需要保留草稿时，应明确草稿所有权和恢复方式。

### R7 · P2 · Schema 与依赖检查的保障低于契约承诺

依据：架构 §6.4 要求输入、输出校验；§11 要求通过工程检查约束依赖；SDK 声明持有可序列化 JSON Schema。

代码位置：

- [Schema 类型](../packages/module-sdk/src/json.ts#L5)
- [Schema 校验](../packages/module-host/src/validate.ts#L16)
- [边界检查](../scripts/check-boundaries.mjs#L20)
- [页面服务客户端](../modules/card-note/ui/client.ts#L9)

只有 Schema 携带 TypeBox `Kind` 符号时才完整校验，普通 JSON Schema 基本只检查是否为对象。临时用例确认：声明 `n` 为数字，传入字符串仍执行成功。SDK 的实际行为因此依赖 TypeBox 的非 JSON 运行时细节。

边界脚本漏掉以下情况，四类临时夹具均被判定通过：

1. 宿主 renderer 通过相对路径导入 main 文件。
2. 模块 UI 通过相对路径导入自身 runtime 文件。
3. 模块根目录 `contracts.ts` 导入 Node 内建模块。
4. 模块 runtime 导入 `@reisa/agent-adapter`。

页面服务没有共享的输入、输出 Schema，DTO 与桥接接口重复描述。`invoke<T>()` 和 `as T` 只提供调用方的类型断言，不能证明 runtime 输出符合类型。卡片笔记迁移文档附录 C.0 也已指出这种类型漂移风险。

建议：支持完整 JSON Schema 校验，或明确收窄契约并拒绝无法校验的 Schema；补解析实际导入目标的边界规则和反例测试；页面动作、DTO 和校验规则使用单一真源。

### R8 · P2 · 错误分支可能泄露私有路径

依据：架构 §10.3 要求详细内部错误留在运行层，不把私有路径或内部数据自动返回模型。

代码位置：

- [宿主异常转换](../packages/module-host/src/host.ts#L185)
- [知识库错误截断](../modules/knowledge/runtime/sync.ts#L392)
- [公开文档信息转换](../modules/knowledge/runtime/index.ts#L428)

宿主直接把 `Error.message` 返回模型。知识库 `safeMessage()` 仅做归一化和截断，文档错误又经公开列表能力返回。文件读取异常可能包含本机绝对路径；正常结果去掉路径，并不覆盖错误分支。

这是源码确认的风险路径，本次未使用真实私有文件或凭据验证泄露。

建议：区分公开错误与内部诊断；内部原因留日志，公开结果返回稳定错误码和安全文案；验证错误路径同样满足数据隔离约定。

### R9 · P2 · 知识库上传大小配置未生效

依据：知识库迁移文档 §7.2、§11 明确要求默认 25 MiB 上传上限。

代码位置：

- [上传大小配置](../modules/knowledge/runtime/config.ts#L24)
- [上传业务服务](../modules/knowledge/runtime/service.ts#L309)

设置页提供 `uploadMaxBytes`，但上传服务没有读取或校验它。临时用例确认：限制设为 1 字节，8 字节文本仍成功写入。

建议：在共享业务服务入口校验配置，使页面上传和 Agent 上传遵守同一规则，并在写入前拒绝超限内容。这是业务输入大小约束，与被排除的 Agent 步数、时间、费用预算不同。

## 6. 模块化与隔离程度

### 6.1 包级边界已成立

SDK、模块宿主、Agent 适配层、基础服务和业务模块职责相对清晰。运行层没有加载 React 页面，UI 入口没有直接加载数据库；模块数据和主会话数据分别持有。知识库的解析、分块、扫描、embedding、存储和业务服务已拆开，卡片笔记的附件、导出和同步也有明确边界。

模块没有绑定框架工具类型，Agent 适配替换不会直接侵入业务模块。但宿主会话存储使用框架 `ModelMessage` 形态，替换框架时仍应评估历史消息格式的适配与迁移成本。

### 6.2 页面服务需要与生命周期机制收敛

当前页面服务注册表位于组合根，没有进入 SDK 生命周期契约；UI 客户端各自描述桥接接口和 DTO，状态检查、错误与取消机制另走一套。

轻量组合根注册表本身可行，不因未采用更重的 UI 命令注册方案而判为错误。但它应与能力调用共享状态检查、在途调用管理、取消、错误和资源释放机制。

注册表目前是模块级全局 Map，未随 `AppRuntime` 实例创建，也未随停用释放。将来多实例测试或运行时重建时，容易出现实例间覆盖与残留，应改为明确的实例所有权。

### 6.3 模块内部仍有集中职责

评审时主要文件规模：

| 文件 | 行数 | 关注点 |
| --- | --- | --- |
| `modules/card-note/runtime/database.ts` | 972 | 数据访问、业务规则、事务、同步 outbox 集中 |
| `modules/knowledge/ui/KnowledgePage.tsx` | 772 | 来源、文档、预览、检索及规则编辑集中 |
| `modules/card-note/ui/NoteEditorView.tsx` | 604 | 编辑器交互与附件状态集中 |
| `apps/desktop/src/renderer/shell/AppShell.tsx` | 532 | 导航、会话、模块状态和多类弹窗集中 |
| `modules/knowledge/runtime/index.ts` | 472 | 初始化、重新配置、能力处理、页面分发、DTO 转换集中 |

数据库集中业务事务是迁移文档的明确选择，不能仅凭文件大就判错。后续拆分应围绕独立用例和事务边界，避免为了分层增加纯透传仓储。

宿主仍有按模块 ID 决定设置弹窗宽度的分支（`AppShell.tsx` 中的 `wide` 判断）。可改为模块贡献元数据，避免专业 UI 需求逐渐扩散到宿主条件分支。

### 6.4 进程层面的性能隔离尚未实现

同步文件读写、SQLite 和批量导入仍在 Electron 主进程执行，数据量增长后可能影响整个应用的响应。这是源码层面的规模风险，本次未进行压力测试。

第一阶段不必给每个模块单独起进程。应先识别明确耗时的解析、导入或索引任务，再迁入 worker，并保持对外能力契约和生命周期行为。

## 7. 建议实施顺序与回归重点

1. **生命周期和失败回滚**：修复 R1、R4，统一工具、页面、后台任务的停用与取消；断言处理器结束前模块不能完成停用，失败后资源释放且注册撤销。
2. **接口范围和真实状态**：修复 R2、R3；收窄配置访问面，统一实时事件与历史状态；覆盖模型流错误、工具失败、取消及历史重载。
3. **宿主状态与 UI 生命周期**：修复 R5、R6；统一默认启用集合，同步能力与状态；覆盖首次启动停用单个模块、重启、连续启停、停用后无页面轮询。
4. **契约与工程保障**：修复 R7、R8、R9；补普通 JSON Schema、越界导入反例、错误脱敏和上传限制的行为验证。
5. **模块内部维护性**：按实际改动频率拆分知识库页面和 runtime 分发职责，将 UI 尺寸等需求移入贡献元数据，再根据压力测试决定 worker 范围。

不要仅以既有测试通过作为问题关闭依据。当前停用测试虽名为“等待结束”，但没有在释放处理器前断言清理尚未发生；模型错误和历史状态的测试也缺少对应失败场景。补充回归应验证外部行为及资源顺序，而非复述实现。
