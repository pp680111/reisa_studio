## R1 · 停用没有等待在途调用结束

**触发场景**：模块运行期间被用户关闭（模块管理开关切到关），且此刻有 Agent 工具调用、页面操作或后台同步在执行。

### 修复前的行为

- **停用瞬时完成**。`ModuleHost.deactivate()`（`packages/module-host/src/host.ts:256`）撤销工具注册、发出取消信号后，立即调用模块清理并置为 `disabled`。宿主不跟踪任何在途调用——`host.ts:252` 的注释虽然写着"等待处理器结束并释放资源"，代码并没有实现。
- **卡片笔记：在库关闭后继续写库**。`#deactivate`（`modules/card-note/runtime/index.ts:86`）先停定时器、立即关闭 SQLite。若此刻 Git 同步在跑（手动"立即同步"或定时同步），它会继续执行"导出变更 → git 提交 → 写入库 → 备份"，全部对着已关闭的数据库句柄：轻则同步静默报错（结果无人接收），重则数据库文件损坏。UI 此时已显示"已停用"，用户看不出异常。
- **页面操作完全不受停用管理**。页面 IPC（`apps/desktop/src/main/index.ts:242`）绕过宿主调用入口，页面服务收不到取消信号、不被登记。停用前后启动的"立即同步"等长耗时 Git 操作照常跑完。
- **"取消"不取消**。`invoke()`（`host.ts:166`）不在执行前检查信号：已取消的调用仍完整执行一次处理器（副作用已发生），最后才对模型返回 `CANCELLED`——模型以为调用取消了，数据实际变了。
- **知识库停用后请求继续打外部 API**。工具处理器拿到取消信号后直接丢弃；embedding 请求不接收信号，且自带最多 4 次重试、429 时最长 30 秒退避。被"取消"的检索可在模块停用后继续请求外部 embedding 服务数分钟。

### 修复后的行为

- 停用变成有顺序的真实过程：置 `deactivating` → 拒绝新调用 → 发取消信号 → **等待该模块全部在途工具调用与页面调用结束**（不设超时上限）→ 调用模块清理（模块内部先取消并等待自己的后台同步，再关数据库）→ 置 `disabled`。
- 已中止的调用在进入处理器前被拦截：直接返回 `CANCELLED`，处理器不执行，零副作用。
- 卡片笔记同步收到取消信号，在阶段边界停下，不再写库/备份；数据库在所有工作排空后才关闭。
- 知识库检索与 embedding 请求被中止，几秒内收尾，不再浪费外部 API 调用。
- 无法立即中断的操作让模块停留在"正在停用"，直到真正结束——状态与事实一致。

**核心差异**：修复前"停用"只是切换状态、留下无人管理的僵尸工作，最坏损坏数据；修复后保证资源释放顺序，代价是停用耗时反映实际在途工作（正常数秒）。

## R2 · 通用模块配置接口形成隔离旁路

**触发场景**：renderer 中任何组件代码发起配置读写。当前无业务调用方，属暴露着的接口面。

### 修复前的行为

- `reisa/module/config/get|set`（`apps/desktop/src/main/index.ts:274`，preload 桥 `apps/desktop/src/preload/index.ts:56`）接受任意 `moduleId + key`：不校验模块状态（停用、failed 的模块配置照样可读写），也不限定调用方只能访问自己模块——同一 renderer 里的代码可以读写任何已登记模块的私有 settings.json。
- 配置句柄保存在模块级全局 Map（`apps/desktop/src/composition/runtime.ts:66`），模块停用后不清理，旁路永久可用。
- 与页面通道形成对照：页面 IPC 有 `!== 'active'` 状态检查，配置通道什么都没有。代码注释自称"仅限本模块 settings.json"，实现并不支持这一约束。

### 修复后的行为

- 移除这条无人使用的通用配置入口；将来模块需要配置 UI 时，注入只能访问自身作用域的客户端，跨模块访问只能走公开能力。
- 对现有功能无感（两个模块的设置页都走页面服务，没有任何代码使用这条旁路）；变化在边界上——renderer 不再存在绕过模块状态与生命周期的配置读写通道，停用模块的配置随之不可访问。

**核心差异**：这是删除旁路而非改变可见功能；修的是"接口面宣称的约束"与"实际行为"不一致。

## R3 · 实时错误与历史状态不一致

**触发场景**：工具调用失败或被取消；模型流中途出错；发送结束后界面重载历史。

### 修复前的行为

- **工具失败在重载后"翻案"**。会话界面在流式事件里能正确把工具标记为"失败"；但发送结束时 finally 中从数据库重载历史（`ConversationView.tsx:291`），而历史转换把所有工具调用硬编码为"已完成"（`ConversationView.tsx:90`），不识别持久化的错误结果。用户会看到同一次调用先显示"失败"、几秒后变成"已完成"。
- 主进程其实单独持久化了工具失败状态（`conversation-manager.ts:195` 记录 `status: 'error'`，并有 `reisa/conversations/toolRecords` 通道暴露），只是历史转换没有使用——数据在，展示丢。
- **模型流错误被记为成功**。适配层 `collectOutcome`（`packages/agent-adapter/src/run.ts:155`）只在收集消息抛异常时返回 error，`finishReason === 'error'` 不参与判定；流中途出现错误事件后 outcome 仍可能是 `completed`。（保留项：最终是否 completed 取决于 AI SDK 的 steps promise 在流错误时 reject 还是 resolve，修复时应实测；代码层不看 finishReason 是确定的。）
- 取消状态同样在重载后丢失。

### 修复后的行为

- 实时事件与历史记录使用同一套状态转换：失败保持失败、取消保持取消，重载后不变。
- `finishReason === 'error'` 纳入失败判定，错误 outcome 如实上报；公开错误信息保留，不再由 UI 重新解释出不同结果。

**核心差异**：修复前"发送过程中看到的"和"发送结束后看到的"可能是两个事实；修复后一致，且以真实结果为准。

## R4 · 激活与重新配置失败缺少完整回滚

**触发场景 A**：模块激活时能力注册校验失败（模块声明有误）。
**触发场景 B**：用户修改知识库设置触发重新配置，且新配置初始化失败（如索引目录不可写）。

### 修复前的行为

- **场景 A**：模块 `activate()` 返回前已创建真实资源——卡片笔记打开了 SQLite 并启动了同步调度器；知识库打开了元数据库、向量库并启动了后台同步。若随后注册校验失败，宿主 catch 只做 Map 删除（`host.ts:241`），`activation.deactivate()` 永不执行：数据库句柄泄漏、后台服务无人停止，模块显示 `failed`。
- **场景 B**：知识库重新配置先停旧服务、关闭旧库，再初始化新服务（`modules/knowledge/runtime/index.ts:154`），无 try/catch。新初始化失败后旧服务已物理关闭、无法恢复；宿主对该模块仍显示 `active`、四个工具仍然注册，但模块内部一切调用抛"未激活"——模块"假活"，所有知识库功能静默失效，只能手动停用再启用恢复。异常只体现为设置保存时报一次错，宿主不知道基础设施出了问题。

### 修复后的行为

- 场景 A：注册校验失败先调用已取得 activation 的 `deactivate()` 释放资源，再进 `failed`——失败也干净。
- 场景 B：重新配置串行化，新服务初始化成功才替换旧服务；失败时要么回滚继续用旧服务，要么向宿主报告基础设施故障（模块转 `failed`、撤销不可用能力、界面显示原因）——不再假活。

**核心差异**：修复前两种失败都把模块留在"名实不符"的状态（failed 但资源泄漏 / active 但半死）；修复后失败要么干净回滚、要么显式暴露。

## R5 · 启用状态默认值不一致，运行状态多份来源

**触发场景**：首次运行（无配置）时停用某个模块；日常查看模块状态与能力计数。

### 修复前的行为

- **首启停一个模块 → 重启后全部被停**。启动时配置缺失 = 默认全启用（`composition/runtime.ts:130`）；启停 IPC 却把缺失配置当作 `[]`（`main/index.ts:173`）。首次运行用户只停用知识库 → 保存的启用清单是 `[]` → 重启后 `[]` 被当成有效配置 → 卡片笔记（用户从未动过）也被停用。
- renderer 有三份状态来源（localStorage 启用列表、宿主配置、运行时状态缓存），启动时要手工对齐两套语义。
- **能力计数冻结**。界面只在启动时取一次能力集合（`AppShell.tsx:98`），启停后不刷新——停用模块后侧栏显示的能力数仍是启动快照。
- **看不到过程与原因**。不订阅宿主状态变化（"正在激活/正在停用"不可见）；模块列表接口其实返回了失败原因，但界面映射时把 `error` 字段丢弃（`AppShell.tsx:100`）——failed 模块只显示"失败"，不知道为什么。

### 修复后的行为

- 缺失配置语义统一（如缺省=全启用），停用时保存完整清单：首次停用单个模块、重启后其余模块不受影响。
- 宿主为唯一运行状态来源：启停后刷新能力集合；订阅状态变化，界面能显示激活/停用过渡状态；失败原因保留并展示。

**核心差异**：修复前存在用户可踩中的状态破坏 bug（首启停一个模块 → 重启全停），且能力计数会撒谎；修复后开关状态跨重启符合预期、计数实时、失败可见。

## R6 · 停用模块的页面只隐藏，没有卸载

**触发场景**：停用某模块后继续使用应用；或启动时某模块未启用。

### 修复前的行为

- 宿主始终挂载全部模块页面，只用 `hidden` 控制显示（`AppShell.tsx:390`）。停用只是看不见，页面活着：知识库页面每 5 秒发 4 个 IPC（来源列表、同步状态、统计、文档列表，`KnowledgePage.tsx:97`），卡片笔记两个视图（`BooksView.tsx:54`、`BookDetailView.tsx`）每 5 秒轮询——全部继续执行。
- 启动时未启用的模块页面同样挂载并轮询，每次调用都得到"模块未激活"错误。
- 页面保留停用时刻的旧数据和旧错误状态。

### 修复后的行为

- 停用即卸载（或至少显式停止全部副作用）：轮询停止，不再有针对停用模块的 IPC 流量；重新启用时重新拉取运行状态，看到新鲜数据。
- 若要保留已启用页面的编辑状态（切页不丢草稿），需明确草稿所有权与恢复方式——这是修复时的设计决策点。

**核心差异**：修复前停用的模块仍在后台产生 IPC 流量和重复报错、界面显示陈旧数据；修复后"停用"意味着页面副作用真正停止。

## R7 · Schema 与依赖检查的保障低于契约承诺

**触发场景**：工具输入不符合声明；代码出现越界导入（CI 环节）；页面 DTO 与 runtime 输出演化不同步。

### 修复前的行为

- **校验强度取决于写法而非契约**。同一个"普通 JSON Schema"声明 `{n: number}`，传入 `{n: "abc"}` 校验通过、工具照常执行：宿主对不带 TypeBox `Kind` 符号的 Schema 只检查"顶层是不是对象"（`packages/module-host/src/validate.ts:15`）。SDK 对外承诺"持有可序列化 JSON Schema"，实际保障却依赖 TypeBox 的非 JSON 运行时细节。（`validate.ts` 注释表明降级是有意的，但与架构 §6.4 的承诺不符。）
- **四类越界导入全部漏检**。边界脚本（`scripts/check-boundaries.mjs`）基于导入说明符的正则匹配：宿主 renderer 相对路径导入 main；模块 UI 相对路径导入自身 runtime；模块根 contracts.ts 导入 Node 内建模块（当前 contracts.ts 恰好无 import，属潜在漏洞）；模块 runtime 导入 `@reisa/agent-adapter`。违规可以静默通过 CI。
- **页面服务无共享契约**。卡片笔记 UI 手写 DTO 和桥接类型，`invoke<T>()`/`as T` 只是调用方断言；runtime 输出走独立序列化加 `as unknown as JsonValue`。当前字段恰好一致，但任何一侧演化都会静默漂移（迁移文档附录 C.0 也指出过）。

### 修复后的行为

- 输入校验二选一：支持完整 JSON Schema 校验（声明数字传字符串 → 明确拒绝 `INVALID_INPUT`），或收窄契约、对无法校验的 Schema 直接拒绝注册——行为确定可预期。
- 边界脚本解析实际导入目标并补反例测试：上述四类越界会被 CI 拦截。
- 页面动作、DTO、校验规则单一真源：runtime 输出变化在编译期或校验期暴露。

**核心差异**：正常使用前后几乎无差异——这条修的是保障网：把"违规/漂移静默通过"变成"必然被拦截"，把"校验与否看写法"变成"看契约"。

## R8 · 错误分支可能泄露私有路径

**触发场景**：工具或页面调用抛出含本机路径的异常（如来源文件不存在、权限错误），错误随工具结果进入模型上下文。

### 修复前的行为

- 两条泄露链，均为已核实的完整闭环：
  1. 宿主把异常 `Error.message` 原样返回模型（`host.ts:189` 的 `describeError`，无脱敏）；
  2. 知识库文档索引失败 → `safeMessage()` 只做 NFKC 归一化 + 300 字符截断（`sync.ts:392`）→ 写入 `document.error` → 经 `list_documents` 工具的**成功结果**返回（`knowledge/runtime/index.ts:428`）→ 进入模型上下文。
- 文件系统错误消息通常含本机绝对路径（如 `ENOENT: no such file or directory, open 'C:\Users\...\xx.md'`）。正常结果里 DTO 已去掉路径，错误分支却不去——不对称。
- 另有 `sync.ts:222` 的 `stat()` 在 try 块之外，原始路径错误直达宿主描述函数。

### 修复后的行为

- 区分公开错误与内部诊断：模型和公开结果只看到稳定错误码 + 安全文案（如"读取来源文件失败"）；含路径的内部原因只写运行层日志。
- 验证错误路径与正常路径满足同一数据隔离约定。

**核心差异**：修复前错误是绕过数据隔离约定的旁路（正常结果不泄露路径、错误结果泄露）；修复后公开面统一为安全文案，排障走日志而非模型上下文。

## R9 · 知识库上传大小配置未生效

**触发场景**：用户在知识库设置里配置"上传大小上限"后上传文件（页面或 Agent 工具）。

### 修复前的行为

- 设置页提供 `uploadMaxBytes`（默认 25 MiB，可保存），但全仓库只有 config 与设置页读写它——上传路径从不读取：`service.upload`（`modules/knowledge/runtime/service.ts:309`）只检查后缀白名单和非空内容，然后直接写盘。把上限设为 1 字节，8 字节文本照样上传成功并进入索引。
- 页面上传（`upload_file` 页面动作）和 Agent 上传（`#uploadDocumentTool`）共用这条路径，双双无限制。对照：相邻的 `autoIndexMaxBytes` 是生效的。

### 修复后的行为

- 共享业务服务入口（两个上传入口共同经过的那一层）校验 `uploadMaxBytes`，超限在写入前拒绝并返回明确错误；页面与 Agent 遵守同一规则。

**核心差异**：修复前该设置是纯装饰（写不读的死配置）；修复后真实生效，且两个入口行为一致。
